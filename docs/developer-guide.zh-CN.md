# 开发指南

[English version](developer-guide.md)

以下原则定义 LocalBridge 的开发方式：

1. 保持核心稳定，让功能可插拔。
2. 文档是交付物的一部分。
3. 每个 Sprint 都必须产出可运行的构建结果。
4. 为五年而设计，而不是为五天而设计。
5. 小提交，清晰的历史。
6. 先接口，后实现。
7. 尽量减少依赖。
8. 模块通过事件通信，而不是直接引用其他功能模块。
9. 配置优先于硬编码。
10. 本地优先：核心工作流不依赖云服务。
11. main 分支不放演示代码。
12. 尽可能优先使用标准库。

## 完成定义（Definition of Done）

当代码、测试、文档和配置示例保持一致，`go test ./...`、`go vet ./...` 及相关平台构建均通过，并且变更
能够作为聚焦的提交进行审查时，才算完成。

## Sprint 流程

```text
设计 -> 实现 -> Review -> 验证 -> 提交
```

每个 Sprint 都要记录目标、交付物、验收标准、已知限制和后续事项。不要用模糊的成功消息掩盖未完成行为。

## 规划流程

战略范围和依赖记录在[产品规划与能力地图](product-plan.zh-CN.md)以及[路线图](roadmap.zh-CN.md)中。
功能只有完成以下顺序后才进入实现：

```text
想法 / 用户问题
  -> 能力与依赖检查
  -> 简短设计说明或 ADR
  -> 公共契约与威胁/隐私审查
  -> Sprint 拆分与验收测试
  -> 实现
  -> Review 与验证
  -> 文档、打包和发布证据
```

### 开始条件（Definition of Ready）

Sprint 满足以下条件后才算准备好：

- 有具体用户场景和可衡量结果。
- 明确范围、非目标、依赖以及回滚/失败行为。
- 如果跨越边界，已经定义数据模型和 API/EventBus 契约。
- 已考虑安全、隐私、保留策略和平台生命周期。
- 测试计划覆盖正常路径、重复、非法输入、对端不可用和重启。
- 已确定中英文文档位置。

### Sprint 记录模板

在 `docs/sprints/` 使用以下结构：

```markdown
# Sprint N — 标题

## 目标
## 用户场景
## 范围
## 非目标
## 契约与数据模型
## 安全与隐私影响
## 实现任务
## 验收标准
## 验证证据
## 已知限制
## 后续工作
```

### Review 清单

Review 时应检查：

- 这部分应该属于核心、传输层还是功能模块？
- 其他客户端是否无需阅读内部代码就能实现该契约？
- 投递状态、幂等、排序、重试和取消是否有明确定义？
- 重启、网络断开、重复投递或能力不支持时会怎样？
- 日志、历史、预览或诊断是否可能泄露私密内容？
- 是否能在不记录载荷正文的情况下观测失败路径？
- 最小可运行发布包和中英文文档是否同步更新？

## 发布流程

打版本前更新路线图状态、变更日志、配置示例、协议文档和已知限制。运行相关单元/集成测试、`go vet`、平台构建
和手工局域网检查。从干净输出目录构建，验证发布包能够启动并提供健康接口/诊断日志，然后记录校验和与回滚说明。

涉及安全的变化必须编写 ADR，并在合并前完成明确审查。功能不能因为路由返回 `200` 就算完成；必须验证端到端用户
结果、失败状态、恢复行为和文档。
